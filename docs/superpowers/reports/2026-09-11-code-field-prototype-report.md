## 3. 实测结果

### 3.1 打字确实是逐字，不是整段出现

用 MutationObserver 记录每一次 token 文本变化，按元素 uid 分组统计变化量：

```
变化量 → 次数:  {"0": 107, "1": 159}
>1 的变化:      无
```

**每次更新只增加 1 个字符，从不出现 +2 或更多。** （`0` 是缩进 token 一次性补齐和类切换造成的。）

### 3.2 行首缩进是瞬现的，不是一个格一个格敲

引擎把整篇文档预先铺进 DOM，只切换可见性 —— 所以缩进**在结构上不可能**逐字出现。实测：

```
缩进 token 出现 @6643ms  →  该行第一个内容字符出现 @6689ms
间隔 = 46ms = 一次基础击键延迟
```

如果缩进是敲出来的，4 个空格要 ~4×18 = 72ms 以上。46ms 证明它是跳过去的。

### 3.3 错字 → 退格 → 重打（把概率临时拉到 1 变成可复现测试）

```
{"打错成":"@r","退回":"@","停多久ms":397,"再打对":"@R"}
{"打错成":"@9","退回":"@","停多久ms":339,"再打对":"@R"}
{"打错成":"\"j","退回":"\"","停多久ms":320,"再打对":"\"/"}
```

打错随机字符 → 停 320–400ms（像人意识到打错了）→ 退格 → 继续打对。

### 3.4 换档顺序：先拉依赖，再打字

```
+    26ms  cf-body is-install        ← 装依赖
+  1973ms  cf-body is-editor         ← 开始打字
+   201ms  is-editor is-selecting    ← 换档时全选（VSCode 选区蓝），停 200ms 后删除
```

顺序正确：**关掉这个项目 → 装依赖 → 打开新文件**。

### 3.5 光标在打字处，后面的代码是透明占位

```
光标已显示: "\"/log\""
后面还有:   1 个 token，总宽 8px
光标x: 192    行尾x: 200     →  ✓ 光标在行尾之前
```

这一条是设计成立的关键：版面从一开始就是最终形状，打字过程中**零重排、零位移**。

### 3.6 行号只跟着已开始的行出现

```
总行数 18（已开始 9 / 未开始 9）
已开始行号 opacity: 1     未开始行号 opacity: 0     未开始行文本 opacity: 0
```

不会出现「空文档却有 18 个行号」这种破绽。

### 3.7 性能：4× CPU 降速下满帧

```
样本 149:  p50=16.7ms  p90=16.7ms  p99=16.8ms  max=17ms
掉帧（>33ms）占比: 0.0%
```

做法：代码层 `transform: translateZ(0)` + `contain: layout paint style` 单独合成，每次 tick 只改一个 span 的 textContent，不跑 rAF 循环。

### 3.8 手机端：零裁切

```
320px  字号11px      可用274px  最长文本258–265px  被裁 0/14 0/22 0/17
390px  字号11.9px    可用344px  最长文本279–286px  被裁 0/14 0/22 0/17
```

为此给代码内容定了**每行 ≤40 字符的硬预算**（已写成检查脚本）。第一次测的时候 320px 下有 5/13 行被裁，最长一行 444px 塞进 274px —— 那不是「有意截断」，是看着像坏了。

### 3.9 减少动效

```
总token 124   仍隐藏 0   行号全部可见 true   光标动画 none   过渡 none
```

直接给出完整代码，零打字、零切档、零过渡。

### 3.10 配色：两个主题都用 VSCode 原生值，全部达标

```
Dark+ 压 #1f1f1f：8 个 token 色 4.95–11.66:1   全 ≥4.5 ✓
Light+ 压 #ffffff：8 个 token 色 4.59–15.15:1  全 ≥4.5 ✓
```

**不需要为了对比度调色** —— 这是「原生 VSCode」能成立的技术前提。VSCode 自己只有界面色不达标，已修正：

```
editorLineNumber #6E7681 → 3.59:1  ❌  改用 #8a9199 = 5.17:1
focusBorder      #0078D4 → 3.64:1  ❌  改用 #4da3e8 = 6.06:1
```

有一处容易改错方向，记下来：

```
#0078D4 压深底 → 3.64 ❌（不能当边框）    #0078D4 + 白字 → 4.53 ✓（可以当填充）
#4da3e8 + 白字 → 2.72 ❌（不能当填充）    #4da3e8 压深底 → 6.06 ✓（可以当边框）
```

### 3.11 终端档和编辑器档确实是两套渲染

```
sw 编辑器: 14 行带行号，0 行终端，10 种语法 token（注解/注释/控制流/函数/关键字/运算符/字符串/类型/变量/空白）
ai 终端:   0 行带行号，20 行终端，语义类齐全：
           t-cmd 1  t-box 6  t-user 2  t-say 4  t-note 2  t-code 2  t-del 1  t-add 2
```

这是「四个方向不是一个东西」最直接的证据：**换方向不只是换文案，是换掉整个渲染面和整套运动**。

## 4. 实测抓到的 10 个问题（都已修）

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 所有字符串 token 高亮错位 | 运算符回退正则 `[^\s\w]+` 是贪婪的，`("` 这样连续的符号会把后面的引号一起吃掉 | 正则排除 `" ' \` # / @`，匹配不到就只吃一个字符，保证一定前进 |
| 2 | 原型页完全没有样式、控制条不工作 | 服务端 CSP 是 `default-src 'self'`，**内联 `<style>` / `<script>` 会被拦掉** | 全部改外部文件。这条对以后所有前端改动都成立 |
| 3 | `window.codefield.pause is not a function` | `id="codefield"` 让浏览器生成同名全局量；引擎初始化失败时 `window.codefield` 静默变成那个 div | div 改名 `#cf-root`；引擎无论如何都定义 API |
| 4 | 静态对照表拿不到 API | 引擎在没有 `#cf-root` 时直接 `return`，什么都不导出 | 拆开：渲染类接口（`paintStatic`）任何页面都有，动画类接口才需要根节点 |
| 5 | 错字只出现一次就再也不出现 | `T.typoP = 0` 是「全局只错一次」，本意是「每个 token 最多错一次」 | 改成 token 上的标记 |
| 6 | 换档时的全选蓝色从来不显示 | CSS 写 `.cf.is-selecting`，JS 把类加在 `.cf-body` 上 | 选择器改成 `.cf-body.is-selecting` |
| 7 | `freeze()` 之后再被覆写 | 冻结没有取消挂起的换档定时器 | `freeze()` 先 `bump()` |
| 8 | `$ claude` 被当成用户提问上色 | 终端的 `type` 步骤写死了 `t-user` | 改走 `termClass()`：`$` 是命令，`>` 才是提问 |
| 9 | 320px 下 5/13 行代码被裁掉 | 代码行长 62–74 字符，可用只有 41 字符 | 给代码内容定 ≤40 字符/行的预算，重写了三段 |
| 10 | 手机端代码字号只有 9.9px | `clamp(9.5px, 2.55vw, …)` 的 vw 系数太小 | 改成 `clamp(11px, 3.05vw, …)`，行号栏 46→30px |

第 1、3、6、8 条都是「看起来只是不好看，其实是错的」那类问题 —— 靠肉眼扫代码很难发现，是探针量出来的。

## 5. 需要你知道的两个让步

### 5.1 打字比真人快得多

屏幕上看得出「一个一个字符出来」的上限大约是**每渲染帧一个字符**（60fps → 16.7ms）。再快就变成「一整块跳出来」，也就不再是打字了。所以 ~18ms/字是**感知上的地板**，不是随便挑的数。

代价：真人 100 WPM 约 120ms/字，一个文档要 40 秒，当背景完全不能用。让步只在速度上，「像人」的线索全部保留：抖动 / 标点与分行后的停顿 / 行首缩进瞬现 / 错字回删。

### 5.2 整轮 71 秒

实测（自然轮播）：

```
软件 14.4s  →  硬件 20.0s  →  算法 18.6s  →  人工智能 17.9s   =  平均 17.7s，整轮 71s
```

每一档里打字是连续可见的，不闷；但**被动看完整轮要 71 秒**。两个应对：

- 已经有交互兜底：点某一档立刻切过去，不等自动轮播
- 想更快就改两个数（`codefield.js` 里 `KEY()` 的区间，和 `afterToken()` 里的标点停顿）

我**没有**为了压时间而砍掉代码 —— 一段完整的、能读懂的代码，比两段半截的更有说服力。

# 第二轮：素材加长、出错删除、思考停顿、验证「全局背景」

上一版有三个真问题，都是对的：

1. **素材太短** —— 代码 14–22 行、依赖日志 8 行。8 行的「拉取依赖」根本不像拉取依赖。
2. **动效是固定速度** —— 逐字打但间隔几乎是常数，看着像机器。
3. **代码看着像一个组件**，不是整个页面的背景。

改完之后还顺手发现了两个真 bug，见 §5。

---

## 1. 素材加长

| | 上一版 | 现在 | 倍数 |
|---|---|---|---|
| 软件 · Java | 14 行 / 329 字符 | **47 行 / 1087 字符** | 3.3× |
| 硬件 · C | 22 行 / 425 字符 | **55 行 / 1115 字符** | 2.6× |
| 算法 · Python | 17 行 / 419 字符 | **46 行 / 1023 字符** | 2.4× |
| 人工智能 · 终端 | 27 步 | **58 步 / 42 行终端输出** | 2.1× |
| 依赖日志 | 8–13 行 | **22–26 行** | 2.4× |

依赖日志现在是真的「拉一阵」：Maven 逐个包下载、apt 的 Unpacking/Setting up、make 的逐文件编译、npx 的包名与审计。

**pip 那档加了 4 条会自己填的下载进度条** —— 这是最「长」的元素，也是最像真的：
填充格数实测 `5 → 10 → 14 → 19 → 23 → 28 → 33 → 34`，`已填 + 未填` 恒定 34 格，
所以右边的标签不会左右跳。

## 2. 固定速度 → 连击模型

不是「加个随机数」就算不匀速。人手是**敲一串、停一下、再敲一串**，所以直接按这个结构排：

```
连击 5–15 个字（16–26ms/字）  →  停顿（140–470ms，偏斜分布：短的多）
偶尔「走神」3.5% 概率 → 停 900–2600ms
```

停顿用偏斜分布而不是均匀随机：均匀随机会让长停顿和短停顿一样多，反而假。

实测（1440px 桌面，20 秒采样）：

```
样本 164:  p10=16  p25=17  p50=19  p75=21  p90=220  p99=791  max=1918ms
快敲(≤32ms) 142    停顿(130–900ms) 22    走神(≥900ms) 1
p50/p90 = 19/220  →  11.6×
```

**p50 是 19ms（快敲），p90 是 220ms（停顿），差 11.6 倍** —— 一眼就看得出不是匀速。
上一版的同一指标是 1.05×。

击键下限卡在 16ms：再快就是一帧一个字（60fps = 16.7ms），看不出是「一个一个」在打。

## 3. 打错 → 删除 → 重打（并且看得见）

两种错法：

| 类型 | 占比 | 过程 | 耗时 |
|---|---|---|---|
| 单字错 | 55% | 敲错 1 个字符 → 停 360–900ms → 退一格 → 重打 | ~0.6s |
| 整词错 | 45% | 敲错 2–5 个字符 → 停 → 逐字退掉 → 重打 | ~1.2–2.4s |

频率 **1/60 字**（≈1.7%，接近真人出错率）。一个 1087 字符的文件约错 18 次，
**额外增加约 20 秒** —— 这正好回答「这样不就有能延长时间了吗」。

关键是**让它看得见**：出错的字符挂上 VSCode 同款的红色波浪下划线。实测计算样式：

```
textDecorationLine: underline
textDecorationStyle: wavy
textDecorationColor: rgb(244, 135, 113)     ← VSCode 的报错红
```

没有这个标记，观众只会看到字符莫名其妙变少，读不出「作者改了个错」，
延长的那 20 秒就变成了「卡顿」。

## 4. 终端档：思考才是主角

编辑器档里「打字」是主角，终端档里「**等**」才是主角。加了三种新的运动：

**思考** —— 转圈 + 秒数 + token 数一起递增，三档共 5.2s + 6.4s + 4.2s + 7.0s ≈ 23 秒：

```
✢ Cogitating… (2s · ↑ 1.0k tokens · esc to interrupt)
```

**流式正文** —— AI 的分析按 chunk 追加，不是整段跳出也不是逐字打字：
实测长度序列 `1 → 5 → 8 → 13 → 21 → 26 → 31 → 36 → 38`。

**工具调用** —— 整块出现（`⏺ Read(...)` / `⎿ Read 128 lines`）。

三种运动互不相同，所以终端档和编辑器档是**看**得出的两回事，不只是文字不同。

## 5. 抓到的两个真 bug

### 5.1 错字概率的钩子是坏的

```js
// 错的：
if (Math.random() >= PACE.corr.p * typoScale()) return false;
//   CODEFIELD_TYPO_P = 1  →  实际概率 0.0105，不是 1

// 对的：
const corrP = () => typeof window.CODEFIELD_TYPO_P === 'number'
  ? window.CODEFIELD_TYPO_P : PACE.corr.p;
```

本意是「可以直接覆盖概率」，写成了「乘一个系数」。后果是**钩子没法把概率拉满也没法关掉**，
于是这个效果既不能做回归测试，我自己的验证也一直是 0 命中 —— 差点被当成「概率低而已」放过去。
现在设 0 就完全不出现，设 1 就必定出现。

### 5.2 内联 `style` 属性会被 CSP 拦掉（但 CSSOM 不会）

```
directive: style-src-attr    blocked: inline
file: codefield.html   line: 28 / 100 / 102
```

是我写在预览 HTML 上的三个 `style="..."`。教训分两层：

- **HTML 里的 `style` 属性一律不要用**，全写进样式表。
- 但 `el.style.setProperty('--x', v)` 这类 **CSSOM 操作是允许的**（实测 `--probe` 能读回来、
  `transform` 生效）。所以「被拦的是内联样式属性」，不是「JS 不能碰样式」——
  我一开始把这两件事混了，好在跟随滚动改用了 `scrollTop`，反而更省心。

顺带确认：跟随滚动用 `scrollTop` 是有效的，实测
`scrollTop: 0 → 20 → 42 → 64 → 85 → 107 → 151`（内容到底之后自动上移）。

## 6. 验证「代码是全局背景，不是组件」

原型页整个重搭了，现在是**四个区块的完整页面**：
hero → 方向 → 流程 → 报名，代码层 `position: fixed`、`z-index: 0`、贯穿整页，
**区块与区块之间的 96px 缝里露出的是未被遮挡的活代码**。

```
position: fixed        覆盖: 0 × 0 × 1440 × 900     父节点: BODY
zIndex: 0              pointerEvents: none
页面总高 2302px = 2.56 屏   代码层始终铺满视口
缝高: [96, 96, 96, 96, 96]
```

区别就在这个缝：如果代码只是某个区块里的装饰，区块之间必然是空的；
现在它**在每一块内容之间都在**，这才是背景。

```
软件 @ 0.0s  →  硬件 @ 92.0s  →  算法 @ 208.1s
平均每档 104s（上一版 17.7s）  →  整轮约 7 分钟
```

# 第三轮：整行重写、明确的暂停、代码带只占页面上侧

四条修改，其中两条改掉了真 bug。

## 1. 代码带不再是全屏，只占页面上侧一小部分

| | 之前 | 现在 |
|---|---|---|
| 定位 | `position: fixed; inset: 0` | `position: absolute; top: 0`（跟着页面滚，滚下去就离开视野） |
| 高度 | 整个视口 | `clamp(240px, 40vh, 380px)` |
| 占整页 | 100%（贴住的） | **13–18%** |
| 底部 | 硬边 | 渐隐到纯黑 |

底部用 `mask-image` 渐隐，**遮罩盖的是整个带子（连底色一起）**，所以不是「被切一刀」，
而是代码和底色一起溶进页面的纯黑里。页面底色也改成了真黑 `#000`。

实测：

```
320px   带子 240px = 视口 42% = 整页 13%   hero 面板顶 184  与渐隐区重叠 56px
390px   带子 338px = 视口 40% = 整页 18%   hero 面板顶 282  与渐隐区重叠 56px
1440px  带子 360px = 视口 40% = 整页 17%   hero 面板顶 304  与渐隐区重叠 56px
```

「重叠 56px」是设计的一部分：面板压住渐隐区的下缘，所以代码带的右下角还露着，
而不是被面板一刀切断。

### 由此修掉的 bug：`--cf-h` 定义错了元素

窄屏下面板位置比预期低了 44px。原因：

```css
/* 错的：--cf-h 定义在 .cf 上，而 .cf 和 .hero 是兄弟 */
.cf   { --cf-h: 240px; }        /* 320px 时 */
.hero { padding-top: calc(var(--cf-h, 340px) - 56px); }
/* 自定义属性不跨兄弟继承 → .hero 读到的一直是兜底值 340px */
/* 340 - 56 = 284，正是实测到的面板顶位置 */
```

修法是把 `--cf-h` / `--cf-fade` 移到 `:root` 定义一次，两边都读得到。

## 2. 「从下往上」修掉了 —— 现在是从上往下长

原因是 CSS：

```css
/* 之前 */
.cf-body.is-terminal, .cf-body.is-install {
  display: flex; justify-content: flex-end;   /* 底对齐 */
}
```

底对齐 = 第一行出现在带子**底部**，然后往上长。实测确认过：

```
之前  行10 首行top=197  末行top=...   ← 内容吊在底部
现在  行10 首行top=  0  末行top=197   ← 从顶部开始往下长
```

现在改成顶对齐往下长，超出后才往上滚（`followBottom` 设 `scrollTop`）。
实测日志从 10 行 → 26 行：首行始终 `top=0`，scrollTop `19 → 128 → 259 → 325 → 368`。
编辑器档同样：首行 `top=0`，最后一行 `top=44` → **从上往下**。

另外可滚动区只占带子的**上部**（`.cf-body { bottom: 36% }`），
底边留给渐隐区 —— 正在打的那一行必须待在完全清晰的位置，
不然最新的内容反而最看不清。

## 3. 整行重写

和「打错一个字」是两回事，所以给了两套完全不同的表现：

| | 打错（手滑） | 整行重写（改主意） |
|---|---|---|
| 错的单位 | 1 个字符（45% 是 2–5 个字符） | **一整行** |
| 停顿 | 360–900ms | **700–2100ms** |
| 删除方式 | 逐字退格 | **全选 → 删掉**（VSCode 选区蓝） |
| 频率 | 每 60 字约 1 次 | 只对 `doc.rev` 标了的行，一行最多一次 |
| 重打的内容 | 同一个 token | **另一个版本** |

最后一条是关键：重写后的内容必须是**真的改过**，不能是同一行再打一遍 ——
那样看起来像卡住了。所以重写内容来自数据里的 `rev`：

```
sw  '// 密码比对交给编码器，别自己写 =='  →  '// 别自己写 ==，用编码器'
    '        if (u.locked()) {'          →  '        if (u.locked() || u.dead) {'
    '            log.warn("locked");'     →  '            log.warn("locked out");'
hw  '    if (len % 4u != 0u) {'          →  '    if ((len & 3u) != 0u) {'      ← 位与代替取模
    '    R(FLASH_CR) |= PG;'             →  '    R(FLASH_CR) |= PG | EOPIE;'
al  '    return 1 << (bits // 2)'        →  '    return 1 << (bits >> 1)'      ← 移位代替除法
    '    bound = min(limit, 2 ** (bits // 2))' → '    bound = min(limit, 1 << (bits >> 1))'
```

都是**真的改进**，不是换个写法。看的人能看出「他改主意了」。

`rev` 用**原文当键**而不是行号 —— 中间插一行就全错位了。
实测三档全部挂上：`sw 3/3`、`hw 2/2`、`al 2/2`。

端到端实测（把概率拉到 1）：

```
全选那一拍文本: "// 密码比对交给编码器，别自己写 =="
重写后该行文本:   "// 别自己写 ==，用编码器"
选区蓝计算值:  background rgb(38,79,120) = #264f78（VSCode 原生选区色）, color transparent
行号完好:      47 行, 已开始 8, 未开始行号 opacity 0, 已开始 1
```

新增钩子 `window.CODEFIELD_REWRITE_P`（0 关掉，1 标了的行全重写）。

## 4. 暂停说得更明确，而且不再「滚到顶部就重开」

### 修掉的 bug：暂停会把内容重演一遍

之前的做法是暂停时 `bump()` 取消定时器、恢复时 `switchTo()` 重新开始。
后果就是你说的「滑到最上面也暂停/不合理」—— 滚回顶部不是恢复，是**从头再演一次**。

现在暂停**不取消定时器**，而是让它原地等：

```js
function later(ms, fn) {
  const my = S.step;
  S.timer = setTimeout(() => {
    if (my !== S.step) return;              // 真的被取消了（换档）
    if (isPaused()) return later(220, fn);  // 暂停中：原地等，恢复后接着跑
    fn();
  }, ms);
}
```

实测恢复行为：

```
失焦前 内容 651 字符   →  恢复后 1051 字符     ← 在继续打，不是掉回 0
滚到底暂停(理由 offscreen) → 滚回顶部 内容 1041  ← 接着演，没重头拉依赖
```

### 暂停规则改成两条，都跟「用户在做别的事」有关，**和滚动位置无关**

1. **正在填表** —— 焦点进表单控件就停，离开 0.8 秒后恢复
2. **代码带不在视野内** —— 观察的是代码带自己，不是内容区块

外加页面切后台、系统减少动效。

延迟 0.8 秒是为了处理 Tab 到下一个字段：中间会瞬间没焦点，
不延迟的话每跳一个字段就恢复一次，背景会一顿一顿地抖。

暂停时钟也修了：要显示秒数的地方改用 `clock()`，暂停期间不走 ——
否则暂停 30 秒回来，思考行会直接跳到 30s。

### 暂停徽标

```
input      →  已暂停 · 正在填写表单
manual     →  已暂停 · 手动暂停
offscreen  →  已暂停 · 代码不在视野内
hidden     →  已暂停 · 页面切到后台
reduced    →  已暂停 · 系统开了「减少动效」
```

图标用两段 CSS 画的竖条，不用 `⏸` 这类字符（U+23xx 在等宽字体里覆盖不稳，
可能变豆腐块 —— 这是前面测字形时留下的教训）。
徽标在 320 / 390 / 1440 三个宽度都实测过：不溢出带子、不和文件名相撞。

### 又修掉一个 bug：API 和界面对不上

```js
// 错的：
Object.assign(API, { get paused() { return isPaused(); } });
// Object.assign 取的是 getter 的**当前值**，不是 getter 本身。
// 结果 API.paused 永远是初始化那一刻的 false，
// 而徽标是直接读 S.reasons 画的 —— 界面说「已暂停」，API 说「没暂停」。

// 对的：
Object.defineProperty(API, 'paused', { get() { return isPaused(); } });
```

这个是探针把 `{paused: false, 徽标: 「已暂停 · 正在填写表单」}` 一起打出来才发现的。

# 第四轮：整体改成玻璃质感，背景不再推动版面

两条反馈都指向同一个根因：**代码带在跟内容抢位置**。

## 1. 背景不再推动卡片

```
之前：.hero { padding-top: calc(var(--cf-h) - 56px) }
      → 版面要给背景让出高度，卡片被推下去（这就是「因为背景导致卡片往下移」）

现在：.hero { padding: 18px 14px 0 }      /* 桌面 26px 40px 0 */
```

实测三个视口，卡片顶都在 26px 以内：

```
1440px  代码带 414px  卡片顶 26px   卡片压住代码带 388px
390px   代码带 388px  卡片顶 18px   卡片压住代码带 370px
320px   代码带 300px  卡片顶 18px   卡片压住代码带 282px
```

代码带也从 `absolute` 改回 `fixed`：钉在页面上侧，内容在它上面滑过去 ——
每张卡片往下滚的时候背后都会经过活的代码，而不是只有第一屏能看到。

## 2. 玻璃：两条弯路，都是采像素量出来才发现的

玻璃看着像不像玻璃，**不取决于模糊，取决于玻璃自己能不能被看见**。
这一点我错了两次：

### 弯路一：深色 tint 压在纯黑上

```css
body { background: #000 }                    /* 底色纯黑 */
.panel { background: rgba(14,15,18,.62) }    /* 卡片近黑 */
```

结果：卡片和背景是同一个黑，**除了那道描边什么都看不见**。玻璃质感出不来。

### 弯路二：浅膜 + 提亮背后

```css
.panel {
  background: rgba(255,255,255,.068);
  backdrop-filter: blur(20px) saturate(195%) brightness(1.12);   /* ← 错在提亮 */
}
```

这次卡片是看得见了，但 **文字对比度掉到 2.09:1**。量出来的最亮像素是
`rgb(52,168,255)` —— `brightness(1.12) saturate(195%)` 把背后的代码**放大了**。

### 现在的做法

一句话：**深色 tint 压暗背后，层次靠边缘高光拉，不靠填充色拉**。
这就是真实磨砂深色玻璃的做法 —— 填充压暗，光都在边上。

```css
body    { background: #0a0c12 }              /* 深冷蓝灰，不是纯黑 */
.panel  {
  background: rgba(9,11,16,.62);
  backdrop-filter: blur(20px) saturate(160%) brightness(.85);   /* ← 压暗，方向反了就全错 */
  border: 1px solid rgba(255,255,255,.20);                      /* 玻璃的边缘 */
  box-shadow: inset 0 1px 0 rgba(255,255,255,.26), …;           /* 顶边高光 */
}
.panel::before { background: linear-gradient(148deg, rgba(255,255,255,.085), transparent 52%) }  /* 斜向反光 */
```

另外加了一层**氛围层**（`body::before`）：几团很淡的色斑 + 一层 22px 的点阵。
原因：代码只占带子的左边约 360px 宽，而卡片有 1120px 宽 ——
**卡片大部分区域背后是空的**。氛围层让玻璃到处都有东西可透。

### 一个量错指标的教训

第一版最坏情况测量得出「浅灰文字只有 2.09:1」，看起来是致命问题。
但换个方式再量（扫一排放 18 组参数）发现：**结论对所有参数都不变** ——
无论 tint 从 .56 加到 .90、模糊从 20px 加到 40px，最亮像素都是 0.16 左右。

这说明它根本不是「透过玻璃的代码」。定位那个像素的坐标：

```
最亮像素 rgb(108,114,123)  CSS坐标 x=1, y=0  所在元素 wp（玻璃探针自己）
```

**最亮的是玻璃自己的顶边高光。** 用一个干净的探针（只有 tint + backdrop-filter，
去掉高光和反光）重测，数值才合理：

```
blur  alpha  brightness   代码透过来的最亮  最亮像素        主#e8e8e8 弱#b6bdc7
  20   0.56     0.82          0.036        rgb(22,55,88)     9.96      6.44
  20   0.62     0.85          0.028        rgb(20,48,78)    11.0       7.0    ← 选的这组
  20   0.82     0.82          0.012        rgb(14,29,45)    13.91      9.00
```

`rgb(20,48,78)` 是明显的蓝 —— 代码的颜色真的透过来了，玻璃在起作用。

## 3. 最终对比度（三个视口，对「背后最亮像素」= 最坏情况）

```
1440px  标题 12.08  正文 11.37  小标 6.32  四色标签 6.26–9.07  方向代码 6.44–8.15
390px   标题 12.95  正文 11.79  小标 6.54  四色标签 6.46–9.47  方向代码 6.78–8.27
320px   标题 13.00  正文 12.64  小标 6.60  四色标签 7.19–9.53
```

过程中修掉两个刚好卡在 4.28 / 4.44 的弱灰色：`#8b93a0` 在玻璃顶边高光那一带
（背后最亮 L≈0.029）不够。把弱文字提到 `#a2aab6` / `#b4bcc6`，
并把反光从 .13 收到 .085 —— 两处一起改，现在最小 6.26，有余量。

## 4. 性能：玻璃叠在动画背景上，4× CPU 降速

```
样本 149:  p50=16.7ms  p90=16.7ms  p99=16.8ms  max=33ms
掉帧(>33ms) 占比 0.7%
```

`backdrop-filter` 压在**一直在动的**图层上，按常理是最贵的组合（每帧都要重新模糊）。
实测只掉 0.7% 的帧。可行，原因是模糊区域只有带子那么高，而且代码层是独立合成层。

## 5. 顺手修掉的两个 bug

1. **暂停徽标被钉在代码带里出不来**。`.cf` 上有 `transform: translateZ(0)`，
   它会成为 `position: fixed` 的包含块；再加 `contain: paint`，子元素也溢不出去。
   卡片盖住带子时徽标就被埋了。→ 把徽标搬到 `.cf` 外面，改成视口级浮层。
2. **徽标只显示「已暂停」**，看不出是因为什么停的。
   `elHold` 改成从 `document` 查了，但 `elHoldText` 还是 `root.querySelector` → null。
   现在四种原因都验过：`正在填写表单 / 手动暂停 / 页面切到后台 / 系统开了「减少动效」`。

## 6. 「代码带离开视野就暂停」这条规则删掉了

带子改成 `fixed` 之后永远不会离开视野 —— 留一条永远不触发的规则是死代码，
而且会让人以为它还在起作用。现在停下来的理由只有「用户在做别的事」：

```
正在填表（焦点在表单控件里） / 手动暂停 / 页面切到后台 / 系统减少动效
```

与滚动位置无关。实测聚焦输入框 → `paused=true, reasons=["input"]`，徽标出现在视口内；失焦 0.8 秒后恢复。

# 第五轮：把卡片调透明

原来是 38% 不透明（`tint .62`），确实太厚了 —— 看着像一块实心的深色板，
只是边上有道光。现在是 **78% 不透明**（`tint .22`）。

## 关键在于：模糊越大，反而越能透明

直觉是「想透明就降 tint」，但那样文字就糊在亮代码上了。
实测发现真正的杠杆是**模糊半径**：模糊越大，背后代码的**亮度峰值被摊得越平**，
于是同样的可读性下，tint 可以放得更低。

扫了 `blur 22–34 × tint 0.16–0.56 × brightness 0.68–0.85` 的组合：

| | 透明度 | 弱文字对比 | 透过来的颜色丰富度 (chP99) | 亮度跨度 |
|---|---|---|---|---|
| 旧 `blur 20 / .62` | 38% | 5.45:1 | 36 | 0.0292 |
| 新 `blur 34 / .22` | **78%** | **6.66:1** | **66** | 0.0148 |

**更透明，同时透进来的颜色反而清楚了一倍，文字对比度还升了。**

代价是「亮度跨度」从 0.0292 降到 0.0148 —— 也就是明暗的层次少了，
看到的是更均匀的颜色雾。对磨砂玻璃来说这是对的方向：
颜色在、形状糊，正是毛玻璃的样子。

## 为什么敢把填充调到这么淡

量了一件事：**卡片填充与页底的亮度差只有 0.0015**（rgb(8,9,15) vs rgb(8,14,23)）。
也就是说这张卡片「是不是一块面」**一直**是靠边缘定义的（描边 + 顶边高光 + 外阴影），
不是靠填充。填充从 .62 降到 .22，这个差值只从 0.0012 变到 0.0015。

所以调淡填充几乎不损失卡片感 —— 这是敢调到 .22 的依据。
顺手把边缘顶上来担这个责任：顶边高光 `.30 → .34`，反光 `.085 → .10`。

## 玻璃最终参数

```css
body   { background: #0a0c12 }                    /* 不是纯黑，玻璃才有底可依 */
.panel {
  background: rgba(9,11,16,.22);                  /* 78% 透明 */
```

## 这一轮修的两处，和一处量错

### 弱文字：`#a2aab6` 在代码带最亮处只有 5.05:1

卡片变透之后余量被吃掉了。弱文字整体提到 `#b0b8c4` → 5.91 / 6.40 / 6.58。
**这是第二次遇到同一个约束**（上一轮是 `#8b93a0` 的 4.28）：
玻璃越透，「次级文字」这个层级越窄，弱文字必须有硬下限。

### 暂停徽标：它自己也变透了，文字掉到 3.23:1

徽标沿用卡片那套参数时会出问题 —— **徽标浮在代码带最亮的那一段上**
（带子顶部常有高亮 token），而它里面没有留白可以缓冲。
所以徽标必须比卡片厚得多：`tint .90` + `brightness(.7)` 压暗背后 → 7.06–9.38:1。

**卡片可以很透，小控件不行。** 这是这次的结论，两者不能共用一个参数。

### 量错的一次（值得记下来）

第一版量徽标时，我把 `.cf-hold` 整个用 `visibility: hidden` 藏起来再截图 ——
但 `visibility` 会把元素**自己的背景**一起藏掉，所以我量到的是徽标背后**原生的代码**，
不是「透过徽标底色之后」的东西。数字是 3.23/4.24，看起来像徽标不可读，
其实完全测错了对象。

正确做法：只藏**文字与图标**（`.cf-hold-text, .cf-hold-bars`），保留容器背景。
改完之后同一位置是 7.06–9.38:1。

和上一轮「最亮像素是玻璃自己的高光」是同一类错误：
**探针不能把要测的东西自己也藏掉（或算进去）。**

## 2. 关键：背景不占版面（A/B 证明）

这是上一轮的核心要求。直接做了一次对照实验 —— 把代码带高度从 300px 改到 900px，
量三张卡片的位置和整页高度：

```
带子 300px:  hero-in top=81   #directions top=436   #apply top=2069   页面高=4188
带子 900px:  hero-in top=81   #directions top=436   #apply top=2069   页面高=4188
→ 卡片位置 / 页面高度完全不变 ✓
```

原因是代码带是 `position: fixed`，它的高度不参与任何排版。
`style.css` 里现在**没有任何**基于 `--cf-h` 的留白，并在注释里写明这是禁止事项：

```css
/* ⚠ 注意 padding-top：这里没有基于 --cf-h 的留白。
   任何形式的 padding-top: calc(var(--cf-h) ...) 都是回到旧错误。 */
```

## 3. 落地时补上的东西（原型里没有，真页面才需要）

原型只有四个静态卡片，真页面有 `app.js` 动态生成的 DOM。重写样式表时漏了这些类，
页面加载正常、控制台也干净，但卡片会没有样式 —— 所以是一个字符一个字符对着
`app.js` 的 `className =` 赋值核对出来的：


其中 `.link-card .desc` 的折叠/展开是从 `git show HEAD:public/style.css` 里
取回原来的行为再翻译成新配色的 —— 不是重新发明，避免把交互改掉。

## 4. 修掉的三个真问题

### 4.1 触控目标：7 个低于 44px

重写时把 `.nav a` 写成 40px、`.tab` 没给最小高度（实测 29.8px），
而 `app.js` 生成的 `.open-btn` 只有 19px。三个视口全部回归到 **0 个低于 44px**。

### 4.2 `.reveal` 无条件隐藏 —— JS 挂掉就是一片空白

原来的写法（旧版也这样）：

```css
.reveal { opacity: 0 }           /* 无条件 */
.reveal.visible { opacity: 1 }
```

如果 `app.js` 加载失败或被禁用，整个页面是一片白，而且 Console 里没有任何线索。
`app.js` 第一行本来就加了 `html.js`，所以把它当开关用：

```css
.js .reveal { opacity: 0 }       /* 只有脚本跑起来才隐藏 */
.js .reveal.visible { opacity: 1 }
```

实测（`javaScriptEnabled: false`）：

```
html有js类=false   h1: 1/visible   hero: 1/visible   卡片: 1/visible   ✓
```

### 4.3 主题默认值

前五轮的设计建立在「深色代码带 + 深冷灰底 + 玻璃」上，其中
**「底色不能是纯黑」和「backdrop-filter 要压暗」是玻璃成立的前提**。
系统偏好浅色的浏览器会拿到浅色语法色压在硬编码的深色底上 —— 没有对比度。

所以 `theme-init.js` 的默认值改成固定深色，不再跟随 `prefers-color-scheme`，
并在注释里写清楚浅色主题需要单独设计一轮。用户手动选过仍然优先（localStorage）。
